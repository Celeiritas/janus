## 3. The shared contract (#11 writes it, #13 and #12 read it)
### 3.1 Files
| File | Written by | When | Disk |
|---|---|---|---|
| `$JANUS_STATE/map.json` (default `~/.local/share/janus/map.json`) | `janus map`, `janus ack` | only when a state, the alert set or the acknowledged set changes | disk |
| `$JANUS_STATE/log/doors-YYYY-MM.jsonl` | `janus map` | one line per state change of a door or a room | disk |
| `~/.local/state/argus-ui/alerts/janus.json` (or `$ARGUS_ALERTS`) | `janus map`, `janus ack` | while an unacknowledged unexpected closed door exists | disk |
| `$XDG_RUNTIME_DIR/janus/run.json` | `janus map` | every run: when it ran, how long it took, and the counters for doors waiting on a second probe | **tmpfs** (memory, not disk) |

`run.json` is how the design's promise of "no disk writes when nothing changed" can hold while the two-probe rule still works. The pending counters and the "last probed" time change on every run, so they live in the runtime directory, which is memory. After a reboot the counters start again from zero, which is harmless. If `XDG_RUNTIME_DIR` is unset (a test, or a shell without a session), the fallback is `$JANUS_STATE/run.json`. Every write goes to a `.tmp` file first and is then renamed, as `docs/alerts.md` asks.

`map.json` holds **no tailnet addresses**. The prober reads them fresh from `tailscale status --json` on every run, so the page, its screenshots and the JSON never show one. It still holds the owner's device names, so it is never committed (`.gitignore`, design §8). **This departs from the spec:** design §6a step 1 lists tailnet IPs among the map's data, and design §8 and `CLAUDE.md` both say "`map.json` (it holds tailnet addresses)". It needs the owner's yes (Q4); if he agrees, the #11 pull request edits design §6a and §8 and that line of `CLAUDE.md` to match.

### 3.2 Matching devices
`doors.json` keys are filled from `realm.json` when they are loaded (`{{SERVER}}` becomes the realm's value). A tailnet device matches a key when the key equals its `HostName` (ignoring case) or the first label of its `DNSName`. `Self` is the server. The rooms come out in this order:
1. the server first;
2. then the `doors.json` devices, in file order;
3. then the tailnet devices that are not in `doors.json`, in alphabetical order. These are rooms without doors, as the design says.

A `doors.json` device that the tailnet doesn't know (the example's `tablet`) is a room in the state `absent`, with its note.

### 3.3 States
| Thing | State | Word on the page | Icon | Comes from |
|---|---|---|---|---|
| room | `online` | online | ✓ | Tailscale `Online: true` (`Self` is always online) |
| room | `asleep` | asleep | 💤 | Tailscale `Online: false`. **Its doors are not probed** |
| room | `absent` | not on the tailnet | – | in `doors.json`, missing from `status` |
| door | `open` | open | ✓ | the TCP connect succeeded (2 s); a `serve` door answered its health GET with 2xx; a `taildrop` door's device is online |
| door | `closed` | closed | ✕ | the probe failed and the door's `expect` allows that (`sometimes`) |
| door | `closed` + `unexpected: true` | closed unexpectedly | ⚠ | the probe failed and `expect` is `always`, or `when-online` while the room is online |
| door | `asleep` | asleep | 💤 | its room is asleep or absent |
| door | `unknown` | not probed yet | ? | the first run, or its room just woke, while a closed answer waits for its second probe |

**The two-probe rule (design §0, §6a).** A door's change **to `closed`** happens only after two consecutive probes agree. The first failed probe sets `pending` in `run.json`, and nothing on disk changes. If the next probe also fails, the state changes. If the next probe succeeds, the counter is cleared.

**Three exceptions** (the owner should confirm them, Q2):
- **Any change to `open` is immediate**, from `closed`, `unknown` or a woken room's doors. A connect that succeeded can't be a dropped packet, and the design's reason for two probes is "one dropped packet never makes Argus glare", which only applies to a failure. So a reopened door clears the alert file in the same run, not up to 10 minutes later, and a new map doesn't show "not probed yet" for five minutes.
- **A room going `asleep` or `absent` takes effect at once, and so do its doors** (they become `asleep`). That is Tailscale's word, not a probe.
- **A room leaving `asleep` or `absent` takes effect at once, and its doors become `unknown`** in that same run, then are probed in it. An open door is then `open` at once (the first exception); a failed one stays `unknown` ("not probed yet") until its second probe, never "asleep" inside an online room.

Probes run in parallel threads (stdlib `concurrent.futures`), so a run where every door times out still finishes in under 3 s (#11's done-means).

**`serve` doors** are probed with `GET https://<Self DNSName without the dot><health>`, with a 2 s timeout and the normal TLS check. See blocker B3.

### 3.4 `map.json` (version 1)
```json
{
  "version": 1,
  "changed": "2026-11-09T21:05:00-07:00",
  "line": "6 doors open · 1 closed unexpectedly · 1 closed · desktop asleep",
  "counts": { "open": 6, "closed": 1, "unexpected": 1, "asleep": 3, "unknown": 0 },
  "rooms": [
    { "device": "homeserver", "self": true, "os": "linux", "state": "online", "expect": "always",
      "last_seen": null, "note": null, "uses": [],
      "doors": [
        { "id": "homeserver/jellyfin", "name": "jellyfin", "how": "connect", "port": 8096, "health": null,
          "state": "closed", "unexpected": true, "expect": "always", "since": "2026-11-09T21:05:00-07:00",
          "probe": "connect timeout 2 s", "agents": ["hermes-jellyfin"], "clients": ["phone", "tv"], "note": null }
      ] }
  ],
  "alert": { "doors": ["homeserver/jellyfin"], "since": "2026-11-09T21:05:00-07:00", "acked": [] }
}
```
- **`counts` counts doors, and each door is in exactly one count.** `closed` is the doors closed as allowed; a door closed unexpectedly is in `unexpected` only, never also in `closed`. `asleep` is the doors of asleep or absent rooms. So the five counts add up to the number of doors in `doors.json`. In the example, 6 + 1 + 1 + 3 + 0 = 11 doors.
- A door's `expect` is its own value, or else its room's. `how` is `connect`, `serve` or `taildrop`. `since` is the time of the door's last state change.
- `probe` is the plain text of the last probe that changed something:
  - "connected in 4 ms"
  - "connect refused"
  - "connect timeout 2 s"
  - "health answered 200"
  - "health answered 502"
  - "device online (Taildrop)"
  - "device asleep, not probed"
- **`line`** is the status line, and it is the same text on the page, in Home's status and in `janus map --json`. Its parts, in this order, each left out when it is zero:
  - "N doors open" (`counts.open`; "1 door open" for one)
  - "N closed unexpectedly" (`counts.unexpected`)
  - "N closed" (`counts.closed`, which leaves the unexpected ones out)
  - asleep rooms (rooms, not `counts.asleep`): named if there are 1 or 2 ("desktop asleep"), counted if there are more ("3 rooms asleep")
  - "N not probed yet" (`counts.unknown`)

  When nothing is mapped yet the line is "No doors in doors.json".

### 3.5 Doors log line
These are the design §5 fields, plus `room` for a room's own change (where `door` is null):
```json
{ "t": "2026-11-09T21:05:00-07:00", "device": "homeserver", "door": "jellyfin", "from": "open", "to": "closed",
  "expected": false, "probe": "connect timeout 2 s" }
```

### 3.6 The alert file (#11 writes it, #13 refines it)
The alert set is the doors whose `unexpected` is true and that are **not** in `alert.acked`. While the set has doors, `janus.json` holds:
```json
{ "job": "janus-map", "level": "alert", "since": "<the earliest since in the set>", "link": "map",
  "message": "homeserver's jellyfin door closed unexpectedly (connect timeout 2 s). Open the Map for its history." }
```
- **Two or more doors make one file with one sentence**, never a second file: "2 doors closed unexpectedly: homeserver's jellyfin, desktop's apollo. Open the Map for their history."
- **The set is empty** (every door reopened, or every door acknowledged): the file is removed.
- **The message uses the device names from `doors.json`** after the realm fill. The file never leaves the server. Argus shows `message` as it is (argus-ui `web/js/core.js`, `alertCard`), so placeholders would show up raw.

`janus ack` (#13) does three things:
1. It puts the doors of the current set into `alert.acked`.
2. It removes the file.
3. It exits 0, and also exits 0 when there was nothing to clear. Exit 2 is a failure, for example a broken `map.json`.

An acknowledged door leaves `acked` when it reopens. A door that closes after the acknowledgement makes the file come back ("until the next change", #13).

### 3.7 `janus map` on the command line
- `janus map`: one run (the timer's job). Exit 0 when the run completed, even if it found closed doors, and 2 when it failed. Tailscale being down or `doors.json` being broken is a failure; in that case Janus writes nothing and the previous map stays.
- `janus map --json` prints the map, and `--once` is the Probe now spelling (the same run).

The units:
- `janus-map.service` (`Type=oneshot`)
- `janus-map.timer` (`OnUnitActiveSec=5min`, `Persistent=false`)
- argus-ui's `argus-limits.conf` drop-in, copied unchanged

### 4.2 `plugin.py`
It reads files only and never starts a process on a GET, following `docs/leafy-plugin.md` and Hermes's `plugin.py`.

| Call | Does |
|---|---|
| `GET api/map` (path `""`) | `{ok, map, run, recent}`: `map.json`, `run.json` (last probed, ms) and the newest 50 lines of this month's and last month's doors log. With no `map.json`: `{ok: true, map: null, msg: "No map yet: janus map hasn't run. Probe now draws it."}` |
| `GET api/map/status` | Home: `{"line": map.line, "needs": <alert set not empty>, "action": "Check the closed door"}` (32 characters at most). With no map: `{"line": "No map yet", "needs": false}` |
| `POST api/map/probe` | `systemctl --user start --no-block janus-map.service`, with fixed arguments and no shell (`$JANUS_SYSTEMCTL` in tests). Answers "Probing; the map updates in a few seconds." |
| `POST api/map/seen` | `janus ack` (`$JANUS_BIN` in tests). Answers with what Janus said |
| anything else | 404 `{ok: false, msg: "not found"}` |

### 4.3 The page (`page.js`, `page.css`)
DOM order is the reading and keyboard order.
1. **Status line.** It holds `map.line` and the time of the last probe ("probed 21:05"), and it is the only `aria-live="polite"` region.
2. **Controls**, three buttons:
   - the List / Map toggle (`aria-pressed`);
   - **Probe now** (`api.post('probe')`, then a re-read after 3 s);
   - **Mark seen**, shown only while the alert set has doors.

   Mark seen doesn't change what runs, so it needs no hold-to-confirm.
3. **The rooms list**, always rendered:
   - One `<section>` per room, with an `<h3 tabindex>` that holds the device name and the room state as icon and word.
   - Inside each room, a `<ul>` of doors. Each door is a `<button aria-expanded aria-controls>` that reads "jellyfin · 8096 · ⚠ closed unexpectedly".
   - Opening a door shows its detail right under it: the probe text, the time since, agents, clients, the note, and its lines from `recent`.
4. **The maze**, a `<figure>` placed after the list in the DOM but shown above it in Map view with CSS `order`:
   - It is an inline SVG with `role="img"`, `aria-labelledby` pointing at the status line and `aria-describedby` pointing at a sentence ("The same rooms and doors as the list below.").
   - `tabindex="-1"` everywhere, and `focusable="false"`.
   - The server is the centre room, with the other rooms in a ring. A door is a gap in the wall the two rooms share, with its name written in the gap:
     - open: drawn ajar;
     - closed: a bar across the gap;
     - unexpected: a bar plus ⚠;
     - asleep: the room dimmed, with 💤.
   - Clicking a room or a door focuses the same entry in the list. The figure has no behaviour of its own.

**List or Map.** List is the default under 600 px and Map from 600 px up. A choice that is made by hand is kept in the URL (`#list` / `#map`). In Map view the list stays below the figure, because the list is the page. Under 600 px the maze stacks the rooms in one column, server first, and scales with `viewBox`.

**Keyboard.**
- Tab order: the toggle, Probe now, Mark seen, then the room headings.
- Up and Down arrows (and Left and Right) move between room headings, with a roving tabindex.
- Enter or Space on a heading moves focus to its first door.
- Enter or Space on a door opens its detail.
- Esc closes the detail and puts focus back on its door.

**Reduced motion** (`prefers-reduced-motion: reduce`): no door swing. A state change swaps the icon and the word, with at most a 150 ms opacity fade. Argus's glare is Elaia's own and already follows the setting.

**Colour.**
- Janus's `#4A5568` is used only for borders and headings, never as the only signal of a state.
- Text contrast is at least 4.5:1 on Night.
- Every state carries an icon and a word.
- Hit areas are at least 44 px.

**Argus in the corner and his glare need no code here.** Elaia's side page always puts Argus in the corner, and he glares from `alerts/janus.json` by himself (argus-ui `docs/alerts.md`). The alert card's "Open Map" link comes from `link: "map"`.

`refresh()` re-reads `api/map` every 15 s. When the line changes, it updates the live region once, so screen readers aren't spammed.
